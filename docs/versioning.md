# 版本与发布规则

项目使用 `MAJOR.MINOR.PATCH`（大版本.小版本.补丁版本）的语义化版本号。

- `MAJOR`：不兼容的 API、配置、输出语义或工作流变化。例如删除公开参数、改变 MusicXML 核心语义且旧调用方必须修改。
- `MINOR`：向后兼容的新能力或重要算法升级。例如新增输入类型、增加节奏修复阶段、增加可选配置。
- `PATCH`：向后兼容的缺陷修复、性能改进和文档修正，不增加需要用户理解的新工作流。

`0.x.y` 表示仍在稳定公开契约之前。当前版本为 `0.3.3`：在 `0.3.2` 的音频节奏稳定化基础上，修复 4/4 第一拍/第三拍弱起歧义，恢复短小但真实的三连音，并把证据不足的自动多连音隐藏为纯时序容器；现有 API 参数仍保持兼容。公开 API、默认制谱语义和回归门禁稳定后再发布 `1.0.0`。

## 预发布版本

需要提前验收时使用 SemVer 后缀：

- `0.4.0-alpha.1`：功能仍可能改变；
- `0.4.0-beta.1`：功能冻结，集中修复；
- `0.4.0-rc.1`：候选发布，仅接受阻断性修复。

构建元数据可写成 `0.3.3+20260820.1`，但不会改变版本优先级。

## 单一发布检查

发布时必须同步更新：

1. `pyproject.toml` 的 Python 包版本；
2. `backend/app/__init__.py` 的运行时/API/MusicXML 版本；
3. `frontend/package.json` 与 `frontend/package-lock.json`；
4. `CHANGELOG.md` 的对应版本条目。

正式发布还应提交到 `main`，并创建同版本的 `vMAJOR.MINOR.PATCH` Git 标签（例如 `v0.3.3`）后一起推送。

自动测试 `backend/tests/test_versioning.py` 会阻止上述版本不一致。发布前还应运行后端测试、Ruff、前端测试/类型检查/构建，并用 `rawtest` 与真实语料做节奏、速度、装饰音和 MuseScore 回读回归。
